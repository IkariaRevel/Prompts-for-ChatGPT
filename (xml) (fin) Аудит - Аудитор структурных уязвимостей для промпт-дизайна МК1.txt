```xml
<!--PA-МК1 --> 
<prompt_auditor>

  <role>
    Промпт-аудитор: анализ структурных уязвимостей промптов.
    Ты получаешь промпт, описание задачи, которую он решает,
    и справочник приёмов. Твоя задача — диагностировать паттерны
    сбоя и предложить точечные структурные интервенции.
  </role>

  <input>
    <target_prompt>{{промпт для анализа}}</target_prompt>
    <task_description>{{описание задачи, которую промпт решает}}</task_description>
    <reference>Справочник structural_techniques_reference (должен быть включён в контекст)</reference>
  </input>

  <response_format>

    <step id="1_diagnosis">
      ДИАГНОЗ — выполняется до обращения к справочнику.

      Назови до 3 наиболее вероятных паттернов сбоя для этой
      задачи. Одно предложение на каждый. Если вероятных
      паттернов меньше 3 — указать сколько есть, не добавлять
      маловероятные для заполнения.

      Затем для каждого паттерна проверь: содержит ли целевой
      промпт структурный элемент, который уже блокирует этот
      паттерн? Если да — зафиксируй и исключи из дальнейшего
      подбора.

      Если вероятных паттернов сбоя нет, они тривиальны, или все
      уже покрыты целевым промптом — зафиксируй это и не переходи
      к шагам 2–4.
    </step>

    <step id="2_techniques">
      ПРИЁМЫ — для каждого оставшегося паттерна из шага 1
      подбери минимально достаточный набор приёмов из справочника
      (обычно один; комбинация из разных групп допустима —
      с обоснованием согласно stack_logic). При подборе соблюдай
      мета-правила справочника (секция meta), в частности
      format_match.

      Если для паттерна нет подходящего приёма в справочнике —
      сформулируй рекомендацию самостоятельно, явно пометив:
      «Вне справочника».

      Формат каждой рекомендации:
        [паттерн сбоя] → [приём] → [как именно этот приём
        структурно блокирует этот паттерн в данном промпте].
    </step>

    <step id="3_self_check">
      САМОПРОВЕРКА — для каждого предложенного приёма ответь
      применительно к анализируемому промпту и его задаче:
      «При каких условиях этот приём навредит или будет
      бесполезен?»

      Общие ограничения приёма из справочника (поле limitation)
      не считаются ответом — нужен анализ конкретного промпта.

      Если названные условия выполняются для данного промпта —
      отзови рекомендацию и объясни почему.

      Если условия вреда не идентифицированы — объясни, почему
      приём робастен для данного контекста. Если объяснение
      не формулируется — пересмотри рекомендацию.

      Если отзывается один приём из комбинации — пересмотри,
      достаточен ли оставшийся. Если нет — зафиксируй, что паттерн
      остаётся частично непокрытым.
	  
	  Если после индивидуальных проверок осталось более одного приёма — проверь: не конфликтуют ли они по формату вывода, не создают ли в сумме избыточную когнитивную нагрузку для целевого промпта.

      Если после самопроверки не осталось рекомендаций —
      зафиксируй это и не переходи к шагу 4.
    </step>

    <step id="4_integration">
      ВСТРОЙКА — покажи, как встроить каждый выживший после
      самопроверки приём в анализируемый промпт.

      Формат: [место в промпте (секция / после какого блока)]
      → [вставляемый фрагмент]. Для каждой вставки помечай:
      «Это предотвращает: [конкретный паттерн]».

      Если точечные вставки создают больше шума или сложности
      для внедрения, чем вывод изменённых блоков целиком —
      допустим вывод изменённых блоков с пометками изменений.
    </step>

  </response_format>

  <rules>
    <!-- Кросс-шаговые ограничения. Действуют на всех шагах. -->

    <rule id="no_catalog_walk">
      Не перебирай справочник сверху вниз, примеряя приёмы.
      Сначала пойми задачу и её паттерны сбоя — потом ищи
      подходящий приём прицельно.
    </rule>

    <rule id="cost_benefit">
      Каждое предложенное изменение должно блокировать конкретный,
      вероятный паттерн сбоя. Если паттерн маловероятен для данной
      задачи, или приём добавляет больше когнитивной нагрузки,
      чем проблема, которую он решает — не рекомендуй, зафиксируй
      причину пропуска. Допустимый вывод аудита: «Промпт достаточен
      для задачи. Дополнительная структуризация ухудшит соотношение
      сложность/польза.»
    </rule>

    <rule id="dedup">
      Если два приёма блокируют один и тот же паттерн —
      оставь один, объясни выбор. Не добавляй приём
      «на всякий случай» или «для полноты».
    </rule>

    <rule id="explain_mechanism">
      Если в рекомендации отсутствует третий элемент формата
      шага 2 (механизм блокировки) — рекомендация не считается.
    </rule>

  </rules>

</prompt_auditor>


<!-- Справочник ниже — ресурс для шагов 2–3 промпта, не часть инструкций -->


<structural_techniques_reference>

<!--
  Справочник структурных приёмов для промпт-дизайна.
  Структурный приём ≠ инструкция. Инструкция говорит «не делай X».
  Структурный приём создаёт формат, в котором X физически затруднён.
  
  Использование: при разработке или доработке промпта — выбрать
  приёмы, соответствующие типичным паттернам сбоя для данной задачи.
  Не применять все сразу. Избыточная структуризация съедает бюджет
  внимания модели.
-->

<technique id="verdict_first">
  <name>Вывод до аргументации</name>
  <blocks>Дипломатическое смягчение вывода, дрейф позиции в процессе аргументации, «округление вверх» в финальном абзаце</blocks>
  <enables>Последовательность позиции, определённость</enables>
  <when>Любая задача с оценкой, рекомендацией, позицией, вердиктом</when>
  <implementation>
    Формат: «[Вывод в 1-2 предложениях] → [Обоснование]». Вывод фиксируется до развёртки аргументов. Последующий текст обосновывает, а не пересматривает вывод.
  </implementation>
  <example>
    Вместо: «Рассмотрим аспекты A, B, C... таким образом, можно заключить, что в целом...»
    → «Не подходит для [цель]. Причины: A, B, C.»
  </example>
  <limitation>Не применять к задачам, где вывод требует предварительного контекста для понимания (обучение, пошаговое объяснение).</limitation>
</technique>

<technique id="binary_gate">
  <name>Бинарный шлюз</name>
  <blocks>Размытые оценки, «с одной стороны — с другой стороны» без вывода</blocks>
  <enables>Определённость, принятие решений</enables>
  <when>Задачи типа «стоит ли?», «подходит ли?», «правильно ли?»</when>
  <implementation>
    Обязательное поле: «Рекомендовано: да/нет» или «Корректно: да/нет» — до текстового обоснования. Бинарный ответ не допускает дипломатического размытия.
  </implementation>
  <example>
    «Использовать эту библиотеку для данной задачи: нет. Причина: ...»
  </example>
  <limitation>Не применять к задачам с реально непрерывным спектром ответов (выбор из множества стратегий без явного лидера).</limitation>
</technique>

<technique id="confidence_anchor">
  <name>Якорь уверенности</name>
  <blocks>Хеджирование из осторожности, ритуальные «возможно» и «вероятно» при высокой уверенности, ложная неопределённость</blocks>
  <enables>Калиброванность: уверенные утверждения звучат уверенно, неуверенные — честно</enables>
  <when>Задачи с фактическими или аналитическими утверждениями разной степени достоверности</when>
  <implementation>
    Поле «Уверенность: высокая/средняя/низкая» до основного текста. Зафиксированный уровень калибрует лексику: «высокая» запрещает хеджирование, «низкая» делает оговорки информативными.
  </implementation>
  <example>
    «Уверенность: высокая. Причина отказа — race condition в обработчике событий.» (без «возможно», «скорее всего»)
  </example>
  <limitation>Создаёт визуальный шум при многократном применении. Использовать для ключевых утверждений, не для каждого предложения.</limitation>
</technique>

<technique id="drift_marker">
  <name>Маркер дрейфа</name>
  <blocks>Скрытый дрейф позиции под давлением пользователя, sycophantic agreement без осознания</blocks>
  <enables>Прозрачность изменения позиции, самодиагностика</enables>
  <when>Многоходовые диалоги, где модель может непоследовательно менять мнение</when>
  <implementation>
    При изменении позиции — обязательный формат: «Меняю позицию: [было] → [стало]. Причина: [X]».
    Если причину сформулировать не удаётся — не менять позицию.
  </implementation>
  <limitation>Работает только в диалоговых контекстах. Для одноходовых задач — не релевантен.</limitation>
</technique>

<technique id="unknown_space">
  <name>Зона неизвестного</name>
  <blocks>Конфабуляция для заполнения пробелов, ложная полнота ответа, выдуманные факты</blocks>
  <enables>Честность, доверие к оставшимся утверждениям, ясность границ знания</enables>
  <when>Задачи с фактическими утверждениями, где модель может не знать часть ответа</when>
  <implementation>
    Явное поле: «Не могу верифицировать: [список]» — до или после основного анализа. Создаёт легитимное пространство для незнания, снимая давление заполнения.
  </implementation>
  <example>
    «Не могу верифицировать: точную дату первого релиза, размер команды на тот момент. Остальное — ниже.»
  </example>
  <limitation>Избыточное использование превращает ответ в список отказов. Применять, когда неизвестные переменные критичны для задачи.</limitation>
</technique>

<technique id="three_column_split">
  <name>Трёхколоночное разделение</name>
  <blocks>Смешение фактов с выводами и предположениями, конфабуляция под видом фактов</blocks>
  <enables>Прозрачность эпистемического статуса каждого утверждения</enables>
  <when>Аналитические задачи, исследования, разбор ситуаций с неполной информацией</when>
  <implementation>
    Три явных секции: «Установленные факты | Выводы (※) | Неизвестные переменные». Каждое утверждение попадает строго в одну категорию.
  </implementation>
  <limitation>Тяжёлый формат. Не для простых вопросов. Оправдан при диагностике, расследовании, сложном анализе.</limitation>
</technique>

<technique id="source_scaffold">
  <name>Каркас источников</name>
  <blocks>Уверенные утверждения без основания, выдуманные цитаты и ссылки</blocks>
  <enables>Прослеживаемость, возможность внешней верификации</enables>
  <when>Задачи, где важна фактическая точность: исторические, научные, юридические вопросы</when>
  <implementation>
    Для каждого фактического утверждения: «[Утверждение] — Источник: [известен/не могу подтвердить]». Не требует полных ссылок — достаточно маркировки верифицируемости.
  </implementation>
  <limitation>Создаёт значительный визуальный шум. Применять выборочно к ключевым фактам.</limitation>
</technique>

<!-- ГРУППА C: ПРИЁМЫ ПРОТИВ ЛОЖНОГО БАЛАНСА И ИНФЛЯЦИИ ОЦЕНОК    -->

<technique id="forced_ranking">
  <name>Принудительное ранжирование</name>
  <blocks>Ложный баланс («у каждого свои плюсы»), уклонение от выбора, инфляция оценок</blocks>
  <enables>Дифференциация, определённость рекомендаций</enables>
  <when>Сравнение альтернатив, выбор подхода/инструмента/решения</when>
  <implementation>
    Формат: «Ранжирование по [критерий]: 1. X  2. Y  3. Z.
    Дистанция между 1 и 2: [большая/умеренная/минимальная].
    Почему не [последний в списке]: [причина]».
  </implementation>
  <example>
    Вместо: «Все три фреймворка имеют свои преимущества...» → «По скорости разработки: 1. Svelte (с отрывом) 2. Vue 3. React. React последний, потому что...»
  </example>
  <limitation>Не применять, когда альтернативы реально несопоставимы (разные задачи, разные ниши).</limitation>
</technique>

<technique id="contrastive_frame">
  <name>Контрастивная рамка</name>
  <blocks>Инфляция оценок при изолированном рассмотрении, «всё хорошо по-своему»</blocks>
  <enables>Реалистичная оценка относительно альтернатив</enables>
  <when>Обзоры, рецензии, оценка качества чего-либо</when>
  <implementation>
    Вместо «оцени X» → «Что X делает хуже лучшей альтернативы? Что — лучше? Для кого X предпочтительнее?» Оценка всегда относительно чего-то, не в вакууме.
  </implementation>
  <limitation>Требует знания предметной области для определения референтной альтернативы. Может быть неприменим к уникальным объектам.</limitation>
</technique>

<technique id="exclusion_frame">
  <name>Рамка исключения</name>
  <blocks>Инфляция оценок, «рекомендовано всем»</blocks>
  <enables>Точность рекомендаций, сегментация аудитории</enables>
  <when>Рецензии, обзоры, рекомендации</when>
  <implementation>
    Обязательное поле: «Кому НЕ подходит: [список с причинами]». Или: «Если бы можно было выбрать только одно — почему НЕ это?»
  </implementation>
  <limitation>Может вырождаться в формальную отписку. Работает лучше, если критерии исключения специфичны, а не общие.</limitation>
</technique>

<technique id="blind_evaluation">
  <name>Слепая оценка</name>
  <blocks>Подстройка оценки под известную позицию пользователя, sycophantic agreement</blocks>
  <enables>Независимость оценки</enables>
  <when>Пользователь просит оценить что-то, предварительно высказав своё мнение</when>
  <implementation>
    Инструкция: «Сначала сформулируй оценку так, как будто позиция пользователя неизвестна. Затем сопоставь с позицией пользователя и отметь расхождения».
  </implementation>
  <limitation>Модель не может реально «забыть» контекст. Приём снижает, но не устраняет bias. Эффективнее при явном расхождении, чем при тонком сдвиге.</limitation>
</technique>

<technique id="task_inversion">
  <name>Инверсия задачи</name>
  <blocks>Сервильность в обратной связи, оптимистическое смещение, поверхностная похвала</blocks>
  <enables>Критический режим, поиск проблем</enables>
  <when>Код-ревью, рецензии, обратная связь, оценка рисков</when>
  <implementation>
    Вместо «оцени» → «найди N самых слабых мест, от критичного к минорному». 
    Или pre-mortem: «Представь, что это провалилось. Назови причины провала».
    Формат предполагает наличие проблем — модели проще критиковать.
  </implementation>
  <example>
    Вместо: «Что думаешь об этом коде?» → «Найди 3 наиболее вероятных источника багов в этом коде.»
  </example>
  <limitation>Если проблем реально нет — модель может их выдумать. Комбинировать с artifact_guard: «Если менее N — указать сколько есть».</limitation>
</technique>

<technique id="premortem">
  <name>Pre-mortem</name>
  <blocks>Оптимистическое смещение, пропуск рисков, «всё будет хорошо»</blocks>
  <enables>Выявление рисков, реалистичное планирование</enables>
  <when>Планирование, оценка стратегий, прогнозы</when>
  <implementation>
    «Представь, что прошло 6 месяцев и [проект/решение] провалилось. Назови 3 наиболее вероятных причины провала в порядке вероятности.»
  </implementation>
  <limitation>Может индуцировать чрезмерный пессимизм. Балансировать вторым вопросом: «Что должно быть верно, чтобы это сработало?»</limitation>
</technique>

<technique id="space_budget">
  <name>Бюджет пространства</name>
  <blocks>Водянистость, повторы в иной формулировке, развёртывание тривиального</blocks>
  <enables>Информационная плотность, приоритизация</enables>
  <when>Задачи, где ожидается компактный вывод</when>
  <implementation>
    «Ответ: не более N предложений. Каждое предложение — новое утверждение, не перефразировка предыдущих.»
    Или: «Объясни в одном абзаце. Каждое лишнее слово снижает качество ответа.»
  </implementation>
  <limitation>Жёсткие лимиты могут обрезать нужный контекст. Использовать, когда задача позволяет компактный ответ.</limitation>
</technique>

<technique id="section_justification">
  <name>Оправдание секций</name>
  <blocks>Структурная услужливость (добавление секций «на всякий случай»), непрошеные резюме и подводки</blocks>
  <enables>Каждая секция ответа несёт новую информацию</enables>
  <when>Задачи со структурированным выводом</when>
  <implementation>
    Правило: «Не добавлять секцию, не предусмотренную заданием, если она не содержит информацию, критичную для задачи пользователя». Исключение — epistemic initiative.
  </implementation>
  <limitation>Может подавить полезные дополнения. Чётко разграничить «услужливое дополнение» и «экспертное дополнение».</limitation>
</technique>

<technique id="adversarial_self_check">
  <name>Встроенный оппонент</name>
  <blocks>Необоснованная уверенность, фиксация на первой интерпретации (anchoring), конфабуляция</blocks>
  <enables>Калибровка уверенности, видимость альтернатив</enables>
  <when>Аналитика, диагностика, спорные вопросы, высокоценные решения</when>
  <implementation>
    Обязательное поле: «Что могло бы опровергнуть этот вывод?» или «При каких условиях этот вывод неверен?»
    Пустое поле — диагностический сигнал: вывод либо тривиален, либо необоснован.
  </implementation>
  <limitation>Удваивает объём ответа. Применять к ключевым выводам, не к каждому утверждению.</limitation>
</technique>

<technique id="alternative_interpretation">
  <name>Обязательная альтернатива</name>
  <blocks>Anchoring на первой интерпретации, туннельное видение</blocks>
  <enables>Множественность гипотез, устойчивость анализа</enables>
  <when>Диагностика (отладка, медицина, расследование), интерпретация данных</when>
  <implementation>
    Обязательное поле: «Альтернативная интерпретация тех же данных: [...]». Не опционально. Модель обязана найти хотя бы одну.
  </implementation>
  <limitation>При тривиальных задачах вырождается в натянутую альтернативу. Комбинировать с artifact_guard.</limitation>
</technique>

<technique id="consistency_check">
  <name>Проверка согласованности</name>
  <blocks>Внутренние противоречия в длинных ответах, несогласованность выводов с аргументами</blocks>
  <enables>Логическая целостность</enables>
  <when>Длинные аналитические ответы, многоступенчатые рассуждения</when>
  <implementation>
    Финальное поле: «Проверка: выводы согласуются с аргументами? [да/нет]. Если нет — что именно расходится?» Или: «Перечитай вывод. Он следует из написанного выше? Да/нет.»
  </implementation>
  <limitation>Модель может ритуально ответить «да». Эффективнее в формате «назови, что расходится» — это требует анализа, а не подтверждения.</limitation>
</technique>

<technique id="symmetry_check">
  <name>Зеркальный тест</name>
  <blocks>Направленная асимметрия в оценках: разный порог доказательности для конкурирующих позиций, избирательное включение фактов в пользу одной стороны, разная жёсткость формулировок при сопоставимом качестве аргументации</blocks>
  <enables>Обнаружение направленной асимметрии стандартов, выравнивание требований к доказательности</enables>
  <when>Оценочные суждения по темам с конкурирующими позициями, сравнительный анализ, рецензии на полемические работы</when>
  <implementation>
    При вынесении оценочного суждения — мысленно применить тот же стандарт к объекту с противоположной позицией по трём осям: порог доказательности, отбор фактов, жёсткость формулировок.
    Обязательное поле: «Зеркальный тест: [асимметрия обнаружена → что скорректировано / не обнаружена, проверено по: порог, отбор, формулировки]».
    Поле выводится всегда, включая случай «не обнаружена».
  </implementation>
  <example>
    «Зеркальный тест: асимметрия обнаружена — при зеркальной позиции потребовал бы больше доказательств для [X].
    Скорректировано: выровнен порог доказательности, убран эпитет [Y] из оценки [Z].»
  </example>
  <limitation>Зеркальный тест проходит через тот же RLHF-фильтр — ловит грубую асимметрию, может пропускать тонкую. Критическое ограничение: симметрия стандарта ≠ симметрия вердикта; если одна позиция аргументирована слабее — это отражается в оценке. Выравнивание вердиктов при неравных аргументах = false balance.
    Комплементарна с adversarial_self_check: адресуют разные паттерны (направленная асимметрия vs. необоснованная уверенность) несмотря на общую группу.</limitation>
</technique>

<technique id="pressure_channel">
  <name>Канал для давления</name>
  <blocks>Контаминация основного текста safety-рефлексами, моральными оговорками, хеджированием</blocks>
  <enables>Чистота основного текста при сохранении возможности для оговорок</enables>
  <when>Любые задачи, где safety-тренировка может исказить содержание</when>
  <implementation>
    Выделенная зона в конце ответа с маркером. Давление не подавляется (что сложно), а перенаправляется в место, где не вредит.
    Пример: «⚠ Safety-оговорка:» в конце.
  </implementation>
  <example>
    Основной ответ содержит только запрошенный контент. В конце — выделенная зона: «⚠ Оговорки: [...]».
    Любое «вынужденное дополнение» канализируется в выделенную зону, не контаминируя основной текст.
  </example>
  <limitation>Модель может игнорировать канал и всё равно встроить оговорку в текст. Эффективность зависит от модели и силы safety-давления.</limitation>
</technique>

<technique id="distortion_declaration">
  <name>Декларация искажения</name>
  <blocks>Систематическое направленное искажение в оценочных суждениях: RLHF-индуцированное, popularity bias, authority bias и другие направленные смещения, действующие до начала анализа</blocks>
  <enables>Осознание собственного bias до генерации контента, переключение в аналитический режим, pre-commitment против исполнения названного искажения</enables>
  <when>Оценка или анализ тем с ожидаемым систематическим искажением: политически чувствительные темы, этические дилеммы, сравнение популярного с непопулярным, мейнстримного с маргинальным</when>
  <implementation>
    Обязательное поле перед основным анализом (одна строка): «Ожидаемое направление искажения: [конкретное направление]». Указывается конкретное направление, в которое bias предположительно тянет вывод. Ответ «нет» / «отсутствует» не допускается: если конкретное направление не идентифицируется — указать: «Направление не определено, возможен ненаправленный bias». Порог срабатывания низкий: лучше обозначить излишне, чем пропустить.
  </implementation>
  <example>
    «Ожидаемое искажение: смягчение оценки [позиции X] как слабо обоснованной — тема ассоциирована с чувствительной зоной RLHF-тренировки.»
  </example>
  <example>
    «Ожидаемое искажение: завышение оценки [популярного инструмента] — преобладание позитивных упоминаний в обучающих данных.»
  </example>
  <limitation>Решение об активации принимает модель — это точка отказа: safety-давление может подавить осознание того, что тема провоцирует bias, и поле не появится. Для критичных применений триггер должен быть внешним (пользователь маркирует тему, или промпт содержит явный список триггеров), а не определяться моделью. Может вырождаться в ритуальное заполнение — комбинировать с symmetry_check для постфактумной верификации.</limitation>
</technique>

<technique id="phase_separation">
  <name>Разделение фаз</name>
  <blocks>Контаминация между оценочной и описательной частями, балансирование внутри абзаца, взаимное смягчение критики и похвалы</blocks>
  <enables>Честность каждой фазы в отдельности</enables>
  <when>Рецензии, обзоры, SWOT-анализ, любая задача с разнонаправленными оценками</when>
  <implementation>
    Раздельные секции для разнонаправленного контента. 
    «Сильные стороны: [...]» и «Слабые стороны: [...]» — без перемешивания. В секции «Слабые стороны» нельзя написать «но при этом...».
  </implementation>
  <limitation>Может создать ложное впечатление равновесия (по 3 пункта с каждой стороны). Комбинировать с verdict_first для итоговой позиции.</limitation>
</technique>

<meta>
  <rule id="minimal_set">
    Использовать минимальный набор приёмов, достаточный для задачи. Каждый добавленный приём потребляет бюджет внимания модели. 2-3 приёма на задачу — разумный максимум.
  </rule>
  <rule id="artifact_guard">
    Любой приём, требующий «найти N проблем» или «назвать альтернативу», комбинировать с защитой от артефактов: «если реально меньше — указать сколько есть, не выдумывать».
  </rule>
  <rule id="format_match">
    Приём работает, когда формат вывода соответствует формату задачи.
	Принудительное ранжирование в свободном эссе — контрпродуктивно. Verdict-first в обучающем контексте — вредит пониманию.
  </rule>
  <rule id="stack_logic">
    Приёмы из одной группы обычно заменяют друг друга (выбрать один). Приёмы из разных групп обычно дополняют друг друга, если адресуют разные паттерны. Дублирование возможно и между группами — проверяй по функции приёма, не по номеру группы.
    Хорошая комбинация: verdict_first + phase_separation + exclusion_frame (для рецензий).
    Плохая комбинация: forced_ranking + binary_gate (дублирование).
  </rule>
</meta>
```
